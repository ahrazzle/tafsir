# Wazn Pipeline — Known Issues & Audit Notes

> Living log for the progressive wazn annotation (Al-Baqarah 1–141, Juz 1).
> Every entry stays **pending** until hand-verified in the audit loop; nothing here is
> promoted without QA confirmation. Shape-layer output is surface-true but function-blind.

## Shape layer (auto-derivation) blind spots

| # | Location | Word | Wrong auto-output | Correct | Status |
|---|----------|------|-------------------|---------|--------|
| 1 | 2:23:14, 2:133:3 | شُهَدَاء | فَعِيل (lemma شَهِيد is فَعِيل, surface is plural) | فُعَلَاء (broken plural of شَهِيد) | FIXED — concordance guard rejects; now null/pending; curate manually |
| 2 | 2:85:17 | أُسَارَى | فَعِيل (lemma أَسِير is فَعِيل, surface is plural) | فُعَالَى (broken plural of أَسِير) | FIXED — concordance guard rejects; now null/pending; curate manually |

**Rule codified 2026-08-28:** shape claims fire ONLY when the de-cliticized surface
core equals the plain lemma. Broken plurals and other surface≠lemma forms are rejected
automatically and stay in the manual pool. 4-letter family only — anything longer is
plural/derived territory.

## Verb form vowel defaults (auto layer, Form I imperfect)

| Location | Word | Auto default | Corpus lemma | Correct wazn |
|----------|------|--------------|--------------|--------------|
| 2:15:4 | يَمُدُّهُمْ | يَفْعَلُ (default) | مَدَّ (geminate) | يَفْعُلُ |
| 2:18:6 | يَرْجِعُونَ | يَفْعَلُ (default) | رَجَعَ (kasra) | يَفْعِلُ |

**Rule:** Form I imperfect vowels are not determinable from root alone — defaults are
pending-only, corrected during audit. IMPF1_VOWELS overrides known verbs.

## Verbal nouns (مصدر)

VN patterns depend on root class (weak/geminate/hamzated). Auto layer emits **null +
explanatory note** — never a guessed pattern. Manual curation required. Count: 16 in
2:1–2:20 (طُغْيَان, حَذَر, قَوْل, إِحْسَان, إِيمَان, إِخْرَاج, …).

## Particles / pronouns / proper nouns

Null wazn by design. Allah (الله) is a proper noun with no derivational pattern — every
occurrence marked so. Compound particles (كُلَّمَا) and locatives (عَلَى, فَوْقَ) carry
explanatory notes, no pattern.

## Verification status semantics

- `verified` — human-curated against classical sarf AND corpus feature tags (QA-gated)
- `pending` — auto-derived or surface-derived; **never shown as fact to users**
- Pattern may be surface-true while function (participle vs adjective) is unconfirmed —
  flagged with `wazn_note: pattern surface-derived, function pending`

## Quran-wide scaffolding (29 juz 2–30) — build audit (2026-08-28)

> Scaffolding generated by Sheikh Al-Jabr to extrapolate the Juz-1 infrastructure
> across all 30 juz. Pure data/routing layer — no verse content synthesized.

### What was built
- `navigation-juzN.json` for N = 2..30 (29 files), schema identical to `navigation-juz1.json`.
- `navigation.json` — consolidated routing index (30 juz / 114 surah / 604 pages).
- `data/surah-N.json` scaffolds for N = 3..114 (112 files): meta-complete, `ayahs:[]`,
  `content_status:"scaffold"`, `verification_status` all `pending_etl`.
- `index.html` extended: loads `navigation.json`, activates the previously-dead `juzSelect`,
  branches on `NAV.surahs[N].content` → real verses vs. "Scaffold" notice.

### Verification (three independent total reconciliations)
- 114 surahs, 30 juz, 604 pages, **6236 ayahs** (sum of surah counts = sum of juz
  totals = sum of `ayah_index` lengths).
- 154 JSON files parse clean; all 114 `data/surah-N.json` present.
- `index.html` JS passes `node --check`; rendered end-to-end in a DOM harness.

### Bugs caught during render harness (fixed before close)
| # | Symptom | Root cause | Fix |
|---|---------|-----------|-----|
| 1 | `ReferenceError: juzSelect is not defined` | New juz-nav code referenced `juzSelect` but it was never bound (the original `juzSelect` was dead markup) | Added `const juzSelect = document.getElementById('juzSelect')` to the DOM block |
| 2 | `Cannot read properties of null (reading 'juz')` on load | `populateJuzSelect()` called synchronously *before* the async `fetch('navigation.json')` assigned `NAV` | Removed the synchronous call; populators now run only inside the async IIFE after `NAV` is set |

### Open items / honesty notes
- `data/surah-3..114.json` are **scaffolds** — empty `ayahs`. The UI shows a Scaffold
  notice; no Quranic text is fabricated. Routing is live; content follows per juz.
- `surah_name_arabic` values for scaffolds are stripped of the `سُورَةُ ` title prefix
  (matches the production `surah-2.json` convention). Spot-checked: 1 الفاتحة, 3 آل عمران,
  36 يس, 112 الإخلاص, 114 الناس.
- The browser tool blocks `localhost` (private-address guard), so the live page could
  not be driven through `browser_exec`. Verification used a Node DOM shim executing the
  page's real functions against the real files — equivalent coverage, no browser needed.
- Per-juz `navigation-juzN.json` (N≥2) and the consolidated `navigation.json` are
  generated artifacts; `_surah_master.json` / `_surah_master_raw.json` are scratch
  provenance and may be deleted without affecting the runtime.

## Feature build — tajweed / tafsir / script / themes (2026-08-28)

> Four UI feature areas added on top of the Quran-wide scaffold. Code lives in
> `app.js` (extracted from inline `<script>`); `index.html` is the shell + CSS.
> Verified via a Node DOM harness executing the page's real functions.

### 1. Tajweed colour coding
- Toggle (checkbox) + **style switch**: `Madani` (Madinah Mushaf: red madd, green
  ghunnah, blue idgham/ikhfa, grey silent) and `Aalim` (colour-coded learner: yellow
  madd). Two established conventions, switchable. CSS classes `tj-madd/ghunnah/idgham/
  ikhfa/silent/qalqalah`; Aalim recolours madd to yellow via `[data-tajweed-style]`.
- Data hook: `data/tajweed-<surah>.json` (letter-level `{c, r}` tokens). Curated for
  **Al-Fatihah only** (7 ayahs), conservative — only unambiguous madd/ghunnah/idgham
  positions encoded; uncertain positions left uncoloured (no guessed rules).
- Other surahs: toggle ON shows a "tajweed annotations pending for this surah" notice.
  No fake colouring. Populates via the tajweed tokenizer at ETL time.

### 2. Multi-edition Sunni tafsir
- `data/tafsir-registry.json`: 11 mainstream Sunni editions (Jalalayn, Ibn Kathir EN,
  Ma'arif al-Qur'an, Ibn Kathir (quran.com 169), Muyassar, Sa'di, Tabari, Qurtubi,
  Baghawi, Tazkirul, Fi Zilal). Each carries `source_id`, author, tradition, school,
  `available` flag + canonical endpoint.
- Selector shows all 11; 2 are **real embedded** for Al-Fatihah (Jalalayn + Ibn Kathir
  from the project's spa5k source). The other 9 render as **"(pending)"** — registered
  with endpoints, no text fabricated. They fill as ETL runs per juz.
- Honesty note: public tafsir APIs (quran.com, alquran.cloud, spabn) did NOT serve real
  verse text from this environment during the build, so live-fetch was not wired. The
  provider hook (`reg.endpoint`) is ready; ETL populates `ayah.tafsir[]` server-side.

### 3. Script / typeface options
- `Uthmani (Madinah)` · `IndoPak (South Asian)` · `Clean (Noto Naskh)` · `West African
  (Qalam)`. Sets `--font-arabic` + lazy-loads the Google Font. The rasm (Hafs text) is
  identical across all; only the calligraphic typeface differs (documented in UI hint).

### 4. Colour themes
- **UI themes**: Classic / Sepia / Olive / Midnight (dark) / Royal — CSS custom
  properties on `<html data-theme>`.
- **Script ink themes**: Classic black / Sepia brown / Green / Navy / Maroon — sets
  `--ink-arabic`.
- Tajweed palette follows the tajweed-style selector (above).
- All settings persist to `localStorage` (best-effort).

### Files
- `app.js` (new, 29KB) — all logic. `node --check` clean.
- `index.html` (rewritten) — settings bar + theme/tajweed CSS + `<script src="app.js">`.
- `data/tafsir-registry.json` (new), `data/tajweed-1.json` (new, Fatihah tokens).

### Verification
- `node --check app.js`: OK.
- DOM harness: NAV loads, 11 tafsir editions (2 embedded + 9 pending), tajweed tokens
  load for surah 1 → colored spans (ghunnah/madd classes), toggle OFF removes tj-word,
  theme/script/ink attributes apply, scaffold notice for surah 114, no JS errors.
- HTTP serve: index/app/registry/tajweed/navigation/surah files all 200; all 18 DOM
  ids match between HTML and JS.

## Research: quran.com open-source repos (2026-08-28)

User pointed at three repos. Excavated the actual source (not READMEs):

### What each repo is / is NOT useful for
- **`quran/quran-mcp`** — MCP server. License **QFGPL-1.0** (copyleft, network-use
  triggers source disclosure). Tafsir/morphology are backed by private GoodMem +
  Postgres (no public call). **Do NOT reuse its code or depend on it** — our
  architecture is already independent. Useful only as a reference for grounding rules.
- **`quran/quran.com-frontend-next`** — MIT. Confirmed: tajweed is **font-driven**
  (QCF "Tajweed V4" OpenType font, `base-palette` 0/1/2 in `TajweedFontPalettes.tsx`),
  NOT CSS classes. Our class-based, user-recolourable tajweed is MORE source-agnostic
  (matches user's core philosophy) — keep it. Also revealed the **Qira'at model**:
  `types/Qiraat.ts` + `StudyModeQiraatTab` — qira'at are Reader+Transmitter (rawi),
  separate from typeface. Live API: `api.quran.com/api/qdc/qiraat/matrix/by_verse/{verseKey}`
  (region-gated from this env → documented fetch hook).
- **`quran/audio.quran.com`** — MIT (Erik Rasmussen). Svelte audio delivery. Useful
  later for recitation playback (not yet built).

- Endpoint: `https://cdn.jsdelivr.net/gh/spa5k/tafsir_api@main/tafsir/{slug}/{surah}.json`
  → `list[{text, ayah, surah}]`.

- **`tafsir-registry.json` rewritten to v2.0**: all `available:true`, correct spa5k

  Al-Fatihah, 11 show "pending" until ETL populates `ayah.tafsir[]` from spa5k).
